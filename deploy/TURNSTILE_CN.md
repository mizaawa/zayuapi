# 页面加载与 Turnstile：上线核验

前后端一起发布，无数据库迁移，无需更换现有密钥。保留原有的服务端 Siteverify 校验、限流和访问策略。不要在生产使用测试密钥，不要在失败时跳过验证码。

1. 用无痕窗口访问首页：不应请求 Turnstile。在启用验证的登录页，可以先填写邮箱和密码；拿到有效验证结果前不能提交密码登录。
2. 在测试环境的浏览器 Network 面板临时阻止 `challenges.cloudflare.com` 的验证码脚本。页面应仍可使用，失败后出现“重新验证”。解除阻止后点击重试，应保留表单内容，无需刷新。邮箱验证页的重发和创建账户是两个独立挑战，不应互相解锁。
3. 在启用 CSP 的生产域名刷新登录页。HTML 应返回带对应 nonce 的新文档，CDN 不应强制缓存该 HTML；带哈希的本站静态资源仍可长期缓存。如果旧 HTML 已被边缘缓存，清理受影响的文档即可。

## 仍然失败时，先区分发生在哪一段

- **页面可见，验证码始终未出现**：在受影响设备查看 Network / Console。区分脚本或 iframe 被 CSP 拦截、浏览器扩展拦截、DNS 或连接超时。核对实际域名已获对应站点密钥授权。自定义 CSP 和反向代理都应允许官方挑战脚本及 iframe；不要用通配符、关闭 CSP 或用第三方镜像代替。
- **验证码已完成，提交仍失败**：检查应用服务器到官方 Siteverify 的出站连接、服务端配置及错误码。记录发生时间、页面和错误码即可；不要收集密码、Cookie、验证码令牌或私钥。
- **页面本身慢**：用同一个设备和网络，分别记录文档首字节、本站 JS/CSS 和第三方挑战耗时。首次冷加载和刷新分开比较，不要用构建包体积替代用户实测时延。
