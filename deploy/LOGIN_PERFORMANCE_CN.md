# 登录后仪表盘性能修复

数据库总量 196GB 不能直接确定慢查询原因。代码中已确认的瓶颈是：仪表盘累计统计每次访问扫描该用户全部历史日志，平台统计再次扫描并关联分组、账户；最近 5 条记录原先读取普通分页结果并计算总数；前端等待用户资料后才查询统计，并在统计完成前隐藏其他区块。

## 修复行为

- 登录页使用应用已有的公开设置缓存和并发请求合并，服务端仍负责验证码、二次验证和账号状态检查。
- 首屏请求 `/api/v1/usage/dashboard/stats?include_totals=false`，只统计今天的数据和近 5 分钟性能指标。历史累计字段带 `totals_pending=true`，界面显示占位符。
- 累计统计随后单独加载，不阻塞图表、最近记录、快捷入口。历史查询合并为一次日志扫描，先按分组和账户聚合，再解析有效平台。
- 服务实例按用户、日期、是否累计、监控日志可见性缓存。今日统计缓存 15 秒，累计统计缓存 5 分钟；累计更新时间通过 `totals_updated_at` 返回并显示在数值提示中。
- 同一个缓存键的并发查询合并。每实例最多 8 个今日统计查询、2 个历史统计查询；数据库查询超时分别为 5 秒和 12 秒。繁忙时返回可重试的 503，累计失败时保留首屏数据。
- 趋势和模型统计查询设置 8 秒超时；账户统计和最近记录响应禁止浏览器及共享代理缓存。
- `/api/v1/usage/dashboard/recent` 固定返回近 7 天最新 5 条记录，读取至多 6 条以判断分页，不计算总数。用户 ID 来自鉴权上下文，客户端不能扩大查询范围。
- 保留既有鉴权、用户限流和 API Key 所有权校验。缓存返回独立副本；切换账号、刷新、切换图表日期和离开页面时会取消旧请求并丢弃旧响应。

普通 `/usage` 分页仍保持原有总数语义。统计缓存只用于显示，不参与扣费、余额校验或权限判断。本次无需数据库迁移。

## 上线核验

后端与前端需一起发布。确认浏览器首先发送 `include_totals=false`，随后发送累计统计请求，最近记录请求为 `/usage/dashboard/recent`。

使用有大量历史记录的普通用户核对：首屏和侧栏可立即使用；今日用量正常；累计统计完成后替换占位符；统计失败有重试入口。再用另一个账号核对数据隔离。通过浏览器 Network 和已有 Server-Timing 记录接口耗时。

生产库只读诊断命令：

```bash
psql "$DATABASE_URL" -v login_user_id=123 -f backend/scripts/diagnose-login-performance.sql
```

将 `123` 替换为需要排查的用户 ID。脚本读取数据库与各表、索引大小，索引有效性，死元组、自动清理时间以及连接等待，并仅规划查询。它在只读事务中执行，设置语句与锁等待超时，不执行日志清理或表重写。

优先核对 `usage_logs` 的 `(user_id, created_at)` 索引是否有效，连接是否存在长事务或锁等待，以及最大表是否实际为用量、错误、审计或请求内容数据。196GB 的组成、生产查询计划和磁盘负载需要从生产库取得；本地样本测试不代表生产耗时。

累计统计首次未命中缓存仍需要扫描该用户历史日志。对于 12 秒内无法完成的超大单用户历史，页面会保留今日数据并显示累计统计重试状态；进一步消除这次历史扫描需要在取得实际查询计划后评估持久预聚合和历史回填。

## 本地验证

- 登录验证码、鉴权状态、路由守卫、应用设置与仪表盘：98 项前端测试通过；类型检查、修改文件 ESLint、生产构建通过。
- 后端 repository、handler、server/routes、web 包的单元测试通过；缓存专项测试使用 service 包全部生产源码单独编译执行，覆盖并发合并、取消、容量、用户与可见性隔离、返回副本及当前数据合并。完整 service 测试包在本机编译时超过可用内存，未完成。
- 使用 PGlite PostgreSQL 引擎实际执行仓储中的 SQL，验证今日与累计、隐藏与显示监控日志的四种组合及跨日边界。在 100,008 条日志样本中，今日查询使用已有索引并读取 6 条日志，累计查询读取 50,007 条日志。该样本仅验证计划与扫描范围，不作为生产响应时间承诺。
- Playwright 在 1440px 桌面及 390px 手机视口检查登录、累计统计延迟、加载完成、统计失败状态；无页面运行错误、横向溢出，图表像素非空。
- 本机没有 Docker/生产数据库连接，Docker 集成测试和生产 196GB 数据集验证尚未执行。
